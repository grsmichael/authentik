## 1. 背景与目标

### 1.1 需求来源

动机两条：

1. **了解企业版到底多了什么** —— 明确哪些是"买了 EE 才有"的能力，避免误判。
2. **个人自用场景下解除阻止** —— 想在自己机器上把 EE 功能打开用起来，不受许可限制。

### 1.2 目标（本阶段只做分析，不动代码）

产出可执行的实施方案：改哪几个文件、改法是什么、验收标准是什么、怎么回滚。

### 1.3 非目标

- 不改变任何 EE 功能本身的业务逻辑（只是让它们不再被许可挡住）。
- 不做持久化"破解"（不动数据库里 EE 相关模型的默认行为）。
- 不做对外分发、不做二次销售、不移除任何 `authentik_enterprise` 的 RBAC 权限体系。
- 不处理 FIPS / FedRAMP / SLA 等 Enterprise Plus 的商业服务项（仓库里本就没有对应代码，`website/docs/enterprise/enterprise-features.mdx:9-22` 明确 Enterprise Plus 相对 Enterprise 只差 SLA/支持/协议，产品功能完全相同）。

### 1.4 合规前置说明（必须在实施前确认）

- authentik 的 EE 功能属于商业授权软件，`authentik/enterprise/LICENSE` 与 Authentik Security 的 EE 订阅协议限制其使用范围。
- 删除许可校验**属于"规避技术保护措施"**：技术上可行（校验全程离线、无网络回连），但个人自用也**不构成授权**。
- **合规路线（推荐先走）**：官方提供 **TRIAL 试用许可**（`authentik/enterprise/license.py:56-60` 的 `LicenseFlags.TRIAL` 就是为此存在），向 Authentik 申请一个试用 key 塞进 `/api/v3/enterprise/` 即可在合规前提下完整体验 EE 功能，无需改任何代码。
- 只有当"不想依赖试用 key 续期"时才走技术解除路线，且仅限本机自用、不得对外提供服务。
- 本文只描述技术可行性，**不提供绕过授权的服务或分发**。

## 2. 现状调研结论

### 2.1 授权是怎么验的（结论：离线、不可逆、单点）

| 环节 | 实现 | 位置 |
|---|---|---|
| 根 CA | 仓库自带的自签 X509 证书 `public.pem`，CN = `Authentik Security Inc. Enterprise Licensing Root X1`，有效期到 2123 | `authentik/enterprise/public.pem`、`license.py:44-48` |
| 签名链校验 | 取 JWT 头 `x5c`，`leaf.verify_directly_issued_by(intermediate)` + `intermediate.verify_directly_issued_by(root)` | `license.py:103-112` |
| JWT 验签 | ES384/ES512 + 叶子证书公钥，`aud` 必须等于 `enterprise.goauthentik.io/license/{install_id}` | `license.py:113-137` |
| 实例绑定 | `install_id` 来自 `get_unique_identifier()` | `license.py:51-53`、`authentik/tenants/utils.py` |
| 多许可叠加 | 所有未过期 `License` 行的 internal/external 配额相加，`exp` 取最大值 | `license.py:140-153` |
| 缓存 | key `goauthentik.io/enterprise/license`，TTL 12h | `license.py:40-41`、`242-252` |

**关键判断（决定实施难度）**：

1. 校验**完全离线**，不访问 authentik 的服务器（`website/docs/enterprise/index.mdx:11` 明说 air-gapped 可用）。
2. 私钥**不在仓库里**，所以无法"合法地"自签一张能通过验签的许可 → **不能靠伪造 key 解锁，只能改代码**。
3. 改代码只需动一个语义入口：`LicenseKey.cached_summary().status.is_valid`。

### 2.2 状态机与降级分级

阈值常量：`authentik/enterprise/models.py:24-27`

| 常量 | 值 |
|---|---|
| WARNING_ADMIN_WEEKS | 2 |
| WARNING_USER_WEEKS | 4 |
| WARNING_EXPIRY_WEEKS | 2 |
| READ_ONLY_WEEKS | 6 |

`LicenseKey.status()` 判定优先级（`license.py:180-208`）：**超限 → 过期 → 即将过期 → VALID**

| 状态 | 触发 | 用户可见后果 |
|---|---|---|
| `UNLICENSED` | 无任何 License 记录且 exp=0 | 无横幅，功能全被挡（EE 功能不可用） |
| `VALID` | 在有效期内且未超额 | EE 功能可用 |
| `EXPIRY_SOON` | 2 周内过期 | 管理员金色横幅，功能仍可用 |
| `EXPIRED` | 已过期 < 6 周 | 管理员横幅，`is_valid=False` → **EE 对象不可写** |
| `LIMIT_EXCEEDED_ADMIN` | 超额 ≥ 2 周 | 管理员横幅，`is_valid=False` |
| `LIMIT_EXCEEDED_USER` | 超额 ≥ 4 周 | Admin + User 界面横幅 |
| `READ_ONLY` | 超额/过期 ≥ 6 周 | `EnterpriseMiddleware` 对 `authentik_api` 写请求返回 **400 `denied_license`** |

`is_valid` = `status ∈ {VALID, EXPIRY_SOON}`（`models.py:77-80`）——注意 `LIMIT_EXCEEDED_*` **不算 valid**。

**过期后既有 EE 对象会不会被删？** 不会。`EnterpriseRequiredMixin` 只覆写 `validate()`（create/update 拦截），删除路径没有额外守卫；`READ_ONLY` 时 middleware 只拦写请求，GET 全部放行、显式放行 `LicenseViewSet` / `FlowExecutorView` / `UserViewSet`（`enterprise/middleware.py:41-69`）。即：**能读、不能改、不会丢**。

### 2.5 席位计数规则（决定"会不会被强制只读"）

- 计数 = 排除匿名、非 active 用户后的 internal / external 两类，**分开计、不可互抵**（`license.py:155-168,189`）。
- Agent / 服务账号**不计入**（`enterprise/agents/models.py:45`）。
- 超限**不会直接拒绝建用户**；`EnterpriseMiddleware` 显式放行 `UserViewSet`（`middleware.py:63-65`，有测试 `enterprise/tests/test_read_only.py:196-215` 佐证）。
- 后果是分档降级，见 2.2。注意阈值基准是"最后一条 **VALID** 的 `LicenseUsage` 记录时间"（`license.py:170-178`），首次装许可前若已超额会**立刻**进只读。

### 2.6 官方口径（供交叉核对）

`website/docs/enterprise/enterprise-features.mdx` 把 EE 能力分成四组：Identity & provisioning（Agent accounts、离职自动化、Google/Entra 同步、外部 source、SSF、SCIM OAuth、WS-Fed）、Authentication & network access（PAM、密码历史、mTLS、RADIUS EAP-TLS、Account Lockdown）、Audit & reporting（增强审计、事件地图、CSV 导出、对象生命周期）、Device security（Fleet / Chrome 连接器、本地设备登录、设备合规）。

与 2.4 的源码核对结果**基本一致**，差异：官方标"预览"的功能（Fleet、Lifecycle、PAM、Scheduled offboarding）在代码里同样是硬阻断，没有隐藏的后门。

## 4. 技术方案（待评审）

### 4.1 方案对比

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| P1 · 单点软解锁 | 覆盖 `LicenseKey.status()`，无条件返回 `LicenseUsageStatus.VALID` | 1 处改动同时满足 FR-01~FR-04；前端 summary 也随之 valid，FR-02/FR-03 一并达成 | 语义上"永远 VALID"，若将来想真实反映过期就需改回 | **推荐** |
| P2 · 覆盖 `is_valid` 属性 | 改 `LicenseUsageStatus.is_valid` 恒 True | 同样简单 | middleware 的 `status == READ_ONLY` 判定不受影响，仍需第二处改动，反而不如 P1 | 否 |
| P3 · 伪造许可 JWT | 自签一张通过 `public.pem` 验签的 key | 无需改代码 | 私钥不在仓库，**做不到** | 不可行 |
| P4 · 逐个改 20+ 守卫点 | 在每个序列化器/装饰器里放行 | 精确控制 | 改动面大、升级易冲突、易漏项 | 否 |
| P5 · 只改前端 `hasEnterpriseLicense` | 前端恒 true | 能解锁 B 类，满足 FR-02/FR-03 | **FR-01 不满足**，C 类仍 400 | 否（可作为补充） |

### 4.2 推荐方案（P1）落点

| 文件 | 改动 | 影响面 |
|---|---|---|
| `authentik/enterprise/license.py:180-208` `LicenseKey.status()` | 首行直接 `return LicenseUsageStatus.VALID` | 后端全部守卫（FR-01）+ `/api/v3/enterprise/summary/` 返回值（FR-02、FR-03）+ middleware 永不 READ_ONLY（FR-04） |

不改：`models.py` 的阈值常量、`middleware.py`、各序列化器、`web/` 前端源码。

### 4.3 两种运行形态的落地方式

**形态一 · 源码直跑**（`make run`，宿主机 Python）

改 `authentik/enterprise/license.py` 后 `make run` 自动生效；重启后清缓存（Django cache 需重启进程或 `cache.delete("goauthentik.io/enterprise/license")`）。

**形态二 · 本机 Docker 全栈**（当前部署，镜像 tag 2026.8.3）

镜像是上游发布物，**不含未发布到 main 的改动**；要让容器里的代码也解锁，二选一：

1. **自定义镜像**（推荐）：在 `deploy/` 加一个 `Dockerfile.unlock`（`FROM ghcr.io/goauthentik/server:2026.8.3` + `COPY` 打过补丁的 `license.py` 到 `/opt/authentik/authentik/enterprise/license.py`），compose 用 `build:` 覆盖 `image:`，升级时同步 tag 重放补丁 → 满足 FR-05 / FR-06。
2. **就地改容器**：`docker cp` 补丁文件进 `authentik-server` / `authentik-worker` 后重启。**缺点**：容器重建/升级即丢失，只适合临时试。

> 重要差异：本次分析对象是源码 `2026.11.0-rc1`，而当前运行的是镜像 `2026.8.3`。**必须确认两版 `license.py:status()` 的行号与逻辑一致**，否则要按运行版本另打一份补丁。见「待确认」I-03。

### 4.4 验证方式

- `curl -k https://127.0.0.1:8443/api/v3/enterprise/summary/`（或 9000）看 status 字段。
- 逐条创建 2.4 C 类对象（mTLS stage、SCIM OAuth provider、DataExport、Access Request、Agent）确认不再 400。
- admin 侧边栏 EE 条目可见、无 `Enterprise only` 提示、无 `ak-enterprise-status` 横幅。
- 清空 `License` 表后写接口仍 200（FR-04）。

## 6. 风险

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| 许可条款与合规风险 | 高 | 属规避技术保护措施，仅个人自用；**首选官方 TRIAL 试用 key**（合规且可随时转正）。对外提供服务则明确违法 |
| 上游版本差异 | 中 | 分析基于 2026.11.0-rc1，运行环境是 2026.8.3；实施前必须 diff 两版 `license.py` |
| 升级冲突 | 中 | 升级上游后补丁行号可能漂移；对策：把补丁写成"基于内容的定位替换"而非行号，并在升级后重放验证 |
| 缓存导致的"改了没生效" | 低 | 12h TTL 缓存；对策：重启容器或清 `goauthentik.io/enterprise/license` |
| 功能自身缺陷 | 低 | EE 功能长期处于 CE 仓库中却被许可挡住，未随 CE 一起充分验证；解锁后可能遇到 CE 侧没修过的 bug |
| 性能 | 低 | `status()` 在部分路径被频繁调用；改为常量返回后**开销更低** |
