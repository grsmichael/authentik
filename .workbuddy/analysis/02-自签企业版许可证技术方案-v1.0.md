## 一、需求来源

用户决策：**保留 authentik 的企业版许可机制本身，但自己生成许可证**（而不是申请官方 TRIAL key，也不是改源码让 `status()` 恒真）。

对应 01 中的 `FR-02`（解除 EE 限制）与 `I-04`（技术路线选择），本文档是它们的落地方案。

## 二、为什么不改源码，而要自签 CA

01 里评估的路线一是覆盖 `LicenseKey.status()` 让它返回 `VALID`。那条路能通，但代价是：改一处代码要同时考虑升级重放、以及 20+ 处守卫上游的语义一致性。

自签许可证是把问题推到**信任根**上：authentik 的校验是离线验签、没有网络回连，唯一的信任锚就是容器里那份 `public.pem`。只要自备整套 PKI 把信任根换掉，官方那 20+ 处守卫一行都不用动，全Doc照原样执行。

| 维度 | 改 status() | 自签许可证（本方案） |
|---|---|---|
| 改动的 authentik 源码 | 1 处（license.py） | **0 处** |
| 升级新版要重新打补丁 | 要 | 不用（挂卷即可，除非官方换算法） |
| 与 20+ 处守卫的一致性 | 靠人工保证 | 官方逻辑原样执行（不干预） |
| 过期后行为 | 恒 VALID（不会进只读） | 走官方逻辑：2 周提醒 → 6 周只读 |
| 风险 | 语义漂移 | 信任根被替换（合规见第 9 章） |

## 三、校验机制（代码事实）

出处：`authentik/enterprise/license.py`

| 步骤 | 代码 | 说明 |
|---|---|---|
| 1 | `get_licensing_key()` L44-48 | 读**相对路径** `authentik/enterprise/public.pem`；容器 CWD=`/`，故真实路径 `/authentik/enterprise/public.pem` |
| 2 | `LicenseKey.validate()` L100-107 | 取 JWT header 的 `x5c`；`len(x5c) < 1` 直接拒绝 |
| 3 | L107-110 | `x5c[0]`=叶子证书、`x5c[1]`=中间证书，两级 `verify_directly_issued_by` |
| 4 | L113-130 | 用**叶子证书公钥**验签，算法白名单 `["ES384","ES512"]` |
| 5 | L127 / L133 | `aud` 必须等于 `enterprise.goauthentik.io/license/{install_id}` |
| 6 | `models.py:56` | 入库时 `LicenseKey.validate(key, check_expiry=False)` 复验一次 |

`public.pem` 在本仓库中**只有这一处引用**（grep 已确认），替换它不存在连带影响。

## 四、自签 PKI 设计

```
根 CA（自签，EC P-384，50 年）      ← public.pem 的内容，即新信任锚
   └── 中间 CA（EC P-384，被根签）
         └── 叶子证书（被中间签）        ← 其公钥用于验许可证 JWT
               └── 许可证 JWT（alg=ES512，用叶子私钥签名）
```

要点：

1. **算法**：`ES512` + `secp384r1`，与官方 licenser 一致（license.py L115-118 的注释明确写了官方用 ES512 + secp384r1）。
2. **签名**：pyjwt 的 `ES512` 就是 `ECDSA(SHA-512)` 对 `{header}.{payload}` 签名、输出 raw `r||s`，所以生成端只用 `cryptography` 即可，不必装 pyjwt。
3. **x5c 必须用标准 base64（带 padding）** —— **本方案唯一的踩坑点**：`license.py` 用的是 `from base64 import b64decode`，按标准字母表解码。若像 JWT 段那样用 base64url 编码，一旦出现 `-`/`_` 字符，解码时**会被当作非法字符直接丢弃**，DER 损坏，最终只报一句含糊的 `"Unable to verify license"`。第一版就栽在这里，生成脚本已修正为 `base64.b64encode`。
4. **audience**：必须是当前实例的 `install_id`，取自库表 `authentik_install_id`。本实例：`6282f10e-ff93-4ff1-8d2b-456d084cd411`。
5. **席位**：`internal_users` / `external_users` 声明要 ≥ 实际用户数，否则 `status()` 会走 `LIMIT_EXCEEDED_*` 分支。默认签 50 / 500，个人自用绰绰有余。

## 六、执行与验证记录（2026-09-27）

```bash
# 1) 取 install_id

  "select * from authentik_install_id limit 1"

# 2) 生成
```

## 七、踩过的三个坑（复用价值高）

1. **x5c 编码**（见第 4 章第 3 点）：base64url 会让 DER 静默损坏，报错信息完全指不到根因。生成脚本里已用 `base64.b64encode` 并加断言式自检。
2. **缓存是跨进程的**：`CACHES` 用的是 `django_postgres_cache.backend.DatabaseCache`（不是进程内 cache），所以 **license 状态结论会存进 DB 缓存 12 小时**。改完许可证不清缓存，UI 会继续显示旧的 `unlicensed`。`docker compose restart` 清不掉，必须显式 `cache.delete("goauthentik.io/enterprise/license")`。
3. **API 要 token，basic auth 不管用**：`/api/v3/**` 不走 DRF 的 BasicAuthentication，用 `-u user:pass` 一律 403 `Authentication credentials were not provided`。脚本化入库只能走 UI 或直接在库里插 `authentik_enterprise_license`。

## 九、合规与回滚

**合规说明**：本方案替换了 authentik 的许可信任根，属于规避其技术保护措施；技术上它完全离线、不触碰官方私钥，但个人自用亦不构成授权。官方仍提供 `LicenseFlags.TRIAL` 的免费试用通道（见 `authentik/enterprise/license.py:56-60`），若希望合规体验 EE，申请 trial key 是更干净的选择。本方案服务于本地实验与个人研究环境。

**回滚**（三步，可逆）：

```bash
cd deploy
sed -i '/enterprise-pki\/public.pem/d' docker-compose.yml   # 去掉挂载行
docker compose up -d                                        # 容器回到官方信任根
docker exec authentik-postgresql psql -U authentik -d authentik \
  -c "delete from authentik_enterprise_license;"            # 删掉自签许可证行
docker exec authentik-server ak shell -c "from django.core.cache import cache; \
  cache.delete('goauthentik.io/enterprise/license')"        # 清 12h 缓存
```
